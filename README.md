## Предметная область и прикладная концепция

Компания обслуживает крупные строительные площадки (ЖК Минск-Мир, Северный Берег, мостовые переходы, карьеры). Парк включает экскаваторы, краны, самосвалы, бульдозеры и погрузчики.

Диспетчер решает три разнородные задачи обслуживания потоков техники:
* **Плановая отправка на объекты**: машины распределяются в порядке живой очереди запросов прорабов.
* **Фиксация возврата и откат назначений**: возврат техники на ремонтную базу при сворачивании работ или отмене ошибочных нарядов.
* **Ликвидация аварий и экстренные наряды**: первоочередное выделение машин на критические инциденты вне общей очереди.

Для моделирования этих сценариев стандартные последовательные контейнеры (`vector`, `deque`, `list`) избыточны и небезопасны: они допускают произвольную модификацию элементов по индексам. Использование адаптеров STL гарантирует жесткое соблюдение дисциплины доступа на уровне типов компилятора.

## Архитектура адаптеров: почему не стандартные контейнеры

Адаптер в STL – это не самостоятельная структура данных с собственной схемой выделения блоков памяти. Это шаблонная интерфейсная обертка (wrapper), которая инкапсулирует базовый последовательный контейнер и намеренно скрывает его итераторы.

```
                          ┌──────────────────────────────────────────────┐
                          │          AdapterManager (Диспетчер)          │
                          └──────────────────────┬───────────────────────┘
                                                 │
        ┌────────────────────────────────────────┼───────────────────────────────────────┐
        ▼                                        ▼                                       ▼
 ┌───────────────┐                        ┌───────────────┐                       ┌───────────────┐
 │  std::queue   │                        │  std::stack   │                       │priority_queue │
 │ (Плановая     │                        │ (Журнал       │                       │ (Аварийный    │
 │  очередь FIFO)│                        │  возврата     │                       │  Max-Heap     │
 │               │                        │  LIFO)        │                       │  с функторами)│
 └───────┬───────┘                        └───────┬───────┘                       └───────┬───────┘
         │ Базовый:                               │ Базовый:                              │ Базовый:
         │ std::deque                             │ std::deque                            │ std::vector
         ▼                                        ▼                                       ▼
  Дисциплина FIFO:                         Дисциплина LIFO:                        Двоичная куча:
  front() + pop()                          top() + pop()                           top() + pop()
  push() в хвост                           push() на вершину                       push() за O(log N)
```

### Причины отсутствия итераторов
Итераторы принципиально исключены из интерфейса адаптеров:
* Наличие итераторов позволило бы прочитать или удалить элемент из середины очереди заявок, нарушив принцип справедливости обслуживания FIFO.
* В стеке итераторы позволили бы извлечь данные со дна в обход дисциплины LIFO.
* В приоритетной очереди модификация элемента через разыменование итератора сломала бы балансировку двоичной кучи без пересчета позиций узлов.

### Выбор базовых контейнеров
* **`std::stack`** по умолчанию использует `std::deque`. Также может строиться на `std::vector` или `std::list`, поскольку требует только методов `push_back()`, `pop_back()` и `back()`.
* **`std::queue`** по умолчанию использует `std::deque`. Может базироваться на `std::list`. При этом `std::vector` использовать нельзя: у вектора нет эффективного метода `pop_front()`, а удаление первого элемента вектора приводило бы к сдвигу всего массива за линейное время $O(N)$.
* **`std::priority_queue`** базируется на `std::vector`. Для эффективного просеивания элементов двоичной кучи алгоритмами `std::push_heap` и `std::pop_heap` критически необходим произвольный доступ по индексу (`operator[]`). По этой причине список `std::list` категорически непригоден для приоритетной очереди.

## Устройство трех диспетчерских контуров

### 1. Плановый контур: `std::queue<EquipmentRecord>` (FIFO)
* **Принцип**: First In, First Out – заявка, поступившая первой, первой направляется на объект.
* **Операции**:
  * `push()`: постановка новой заявки прораба в конец очереди;
  * `front()`: просмотр параметров машины, стоящей первой на выезд;
  * `pop()`: снятие обслуженной заявки из головы очереди после отправки машины;
  * `back()`: проверка последней зарегистрированной в системе заявки.

### 2. Журнал возврата: `std::stack<EquipmentRecord>` (LIFO)
* **Принцип**: Last In, First Out – последняя прибывшая на стройплощадку единица техники первой возвращается на ремонтную базу при сворачивании фронта работ.
* **Применение**: откат ошибочных распределений и ведение истории ревизий техники на базе ТО.
* **Операции**:
  * `push()`: регистрация прибытия техники на базу;
  * `top()`: инспекция последней вернувшейся машины;
  * `pop()`: передача машины на очередной объект либо снятие с ревизии.

### 3. Экстренный контур: `std::priority_queue<EquipmentRecord, ...>` (Max-Heap)
* **Принцип**: Двоичная куча с приоритетным извлечением за время $O(1)$ для вершины и $O(\log N)$ для добавления и удаления узлов.
* **Суть**: вне зависимости от времени регистрации запроса, наверх автоматически всплывает техника для устранения аварий (ранг 3 – Аварийно-критический) либо наиболее дорогостоящие наряды.

## Сменные компараторы кучи (Comparators.h)

Для управления дисциплиной двоичной кучи разработаны 4 независимых функциональных объекта (функтора). Каждый функтор перегружает константный оператор вызова `operator()`:

```cpp
// 1. Приоритетный компаратор: аварийный ранг > часовая ставка аренды
struct EquipmentPriorityCompare {
    bool operator()(const EquipmentRecord& a, const EquipmentRecord& b) const {
        if (a.priorityLevel() != b.priorityLevel()) {
            return a.priorityLevel() < b.priorityLevel();
        }
        if (a.hourlyRate() != b.hourlyRate()) {
            return a.hourlyRate() < b.hourlyRate();
        }
        return a.id() < b.id();
    }
};

// 2. Компаратор по тарифу: наиболее дорогая техника на вершине
struct EquipmentRateCompare {
    bool operator()(const EquipmentRecord& a, const EquipmentRecord& b) const {
        if (a.hourlyRate() != b.hourlyRate()) {
            return a.hourlyRate() < b.hourlyRate();
        }
        return a.id() < b.id();
    }
};

// 3. Компаратор по моточасам: техника с максимальной наработкой первой идет на ТО
struct EquipmentHoursCompare {
    bool operator()(const EquipmentRecord& a, const EquipmentRecord& b) const {
        if (a.hoursWorked() != b.hoursWorked()) {
            return a.hoursWorked() < b.hoursWorked();
        }
        return a.id() < b.id();
    }
};

// 4. Компаратор по инвентарному ID
struct EquipmentIdCompare {
    bool operator()(const EquipmentRecord& a, const EquipmentRecord& b) const {
        return a.id() < b.id();
    }
};
```

В классе `AdapterManager` реализован механизм динамического переключения текущего критерия кучи: при выборе режима коллекция мгновенно перестраивается с сохранением всех накопленных записей.

## Неразрушающий обход коллекций

Так как адаптеры STL не предоставляют итераторов `begin()` / `end()`, прямой просмотр табличных данных кажется невозможным. Классическая ошибка начинающих – разрушение структуры при извлечении элементов через `pop()`.

В данном проекте задача решена идиоматично и безопасно:

```cpp
void AdapterManager::queuePrint(std::ostream& os) const {
    if (queue_.empty()) {
        os << "Очередь (std::queue) пуста.\n";
        return;
    }
    EquipmentRecord::printHeader(os);

    // Создание легковесной локальной копии адаптера для обхода
    std::queue<EquipmentRecord> temp = queue_;
    while (!temp.empty()) {
        temp.front().printRow(os);
        temp.pop(); // Извлекаем из локальной копии, оригинал остается нетронутым
    }
    os << "Всего заявок в очереди: " << queue_.size() << "\n";
}
```

Копирование контейнера происходит быстро, гарантируя полную изоляцию и неизменность рабочих очередей диспетчера во время чтения, фильтрации и экспорта.

## Интерактивное меню диспетчера

Главное меню программы объединяет управление всеми потоками:

```text
========================================================================
   ЛАБОРАТОРНАЯ РАБОТА №5: АДАПТЕРЫ КОНТЕЙНЕРОВ STL (Вариант 10)
   Тема: Учет занятости строительной техники в строительной компании
========================================================================
1. Работа с Очередью заявок на выделение техники (std::queue, FIFO)
2. Работа со Стеком журнала возврата техники (std::stack, LIFO)
3. Работа с Приоритетной очередью заявок (std::priority_queue, Heap)
4. Заполнить все контейнеры демонстрационными данными (Seed Data)
5. Сводный отчёт и экспорт всех трёх адаптеров в единый файл
0. Завершить работу и выйти из программы
========================================================================
```

Каждое подменю поддерживает 11 специализированных действий:
1. Табличный просмотр всех элементов структуры;
2. Добавление записи с валидацией реквизитов;
3. Извлечение рабочего элемента (`pop` с выводом параметров);
4. Инспекция граничных элементов (`front`/`back` для очереди, `top` для стека и кучи);
5. Редактирование записи по инвентарному ID;
6. Удаление записи по ID;
7. Полнотекстовый поиск по марке, объекту или категории;
8. Выборка по строительно-монтажной категории;
9. Сортировка контейнера / переключение компаратора кучи;
10. Экспорт содержимого в текстовый отчет;
11. Полная очистка контейнера с подтверждением диалога yes/no.
